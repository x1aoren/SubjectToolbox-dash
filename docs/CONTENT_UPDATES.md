# 云端远程更新内容方案（设计稿）

> 状态：**仅设计，本期未实现。** 当前 STB 只做「发现新版本 → 提示去应用市场」，不下载 APK，也不下载内容包。
> 目的：在不破坏离线体验、不把平板磁盘写满的前提下，给古诗文、词库、语法、公式这类内容留一条可控的更新通道。

## 1. 结论（TL;DR）

1. **APK 不远程更新**：学校平板通过专门市场安装，后台只下发版本号与更新说明，客户端提示去市场更新。
2. **内容与代码分离**：把 `assets/content/` 变成「内容版本 + 文件清单」，客户端只认清单，不认具体文件名。
3. **全量包优先，差分包后置**：第一版只做「完整内容包」的下载、校验、原子替换和回滚；差分包等包体确实到几十 MB 再引入。
4. **按 SN 灰度**：服务端用 `SHA-1(SN) % 100` 分桶，支持 5% → 25% → 100%，也可以对单台设备放行/排除。
5. **Wi-Fi + 空间检查 + 原子替换**：下载到临时目录，校验哈希与签名，校验通过才替换；旧版本保留一份用于回滚。
6. **强上限**：内容包下载最多 200 MB，临时区与旧版本各 1 份，客户端磁盘保留至少 500 MB 才允许更新；失败即停，不无限重试。
7. **内容更新与云端配置解耦**：`/v1/config` 只告诉客户端「有哪个内容版本、灰度是否命中」，真正的下载地址与清单走独立接口，避免每次拉配置都带大 JSON。

## 2. 现状与边界

| 项目 | 现状 |
| --- | --- |
| 客户端内容 | 全部在 APK 的 `assets/content/`（诗词 JSON、语法 JSON、方程式、元素、公式、HTML、两份 SQLite 词库） |
| 网络 | 只有一次 handshake / 事件上报 / 反馈提交；没有内容下载 |
| 磁盘 | 词库由 APK 首启复制到 `databases/`，英汉 86 MB、汉语 15 MB；其余内容在 APK 内 |
| 后台 | 云端配置里有 `content.version`、`content.rollout`、`content.notes`，但客户端只用来展示，不下载 |
| 版本 | 只提示去应用市场，不提供下载地址 |

可以远程更新的：诗词/语法/方程式/公式这类 JSON、HTML 与主题资源。
**不建议**远程更新的：`classes.dex`、原生库、AndroidManifest、任何可执行代码（等于绕过应用市场，风险与合规都不可接受）。
词库属于「大文件、低频更新」，可以走同一套包机制，但要单独限速、单独预算。

## 3. 内容模型

### 3.1 版本

- `contentVersion`：内容包版本，形如 `2026.11.14` 或 `2026111401`；
- `minAppVersion`：这个内容包要求的最低客户端版本，防止新字段被旧代码读崩；
- `channel`：`stable` / `beta`；
- `rollout`：0–100 的灰度比例；
- `notes`：给后台和客户端看的说明；
- `manifestHash` / `signature`：清单与包的完整性凭证。

客户端当前内容版本记在 `manifest.json`，安装包内置版本作为「保底版本」。云端版本高于本地且满足条件才提示/下载。

### 3.2 清单（manifest）

```jsonc
{
  "contentVersion": "2026.12.01",
  "minAppVersion": "1.2.0",
  "channel": "stable",
  "rollout": 100,
  "totalBytes": 18342122,
  "files": [
    { "path": "chinese/poems.json", "sha256": "…", "bytes": 48213 },
    { "path": "formula/formulas.json", "sha256": "…", "bytes": 91204 },
    { "path": "chemistry/equations.json", "sha256": "…", "bytes": 51220 }
  ],
  "package": {
    "url": "https://stb.mcobs.cn/content/2026.12.01.zip",
    "sha256": "…",
    "bytes": 18342122,
    "signature": "ed25519:…"
  },
  "minFreeBytes": 536870912,
  "publishedAt": "2026-12-01T08:00:00.000Z"
}
```

- 文件路径必须相对、不能含 `..`、不能以 `/` 开头；
- 单文件与整包都有上限（例如单文件 100 MB、整包 200 MB）；
- 清单本身也签名，客户端先验签再决定是否下载。

### 3.3 包格式

- 首选 ZIP（store 或 deflate），内部保持 `content/` 相对路径；
- 词库可以单独打一个 `dict-pack.zip`，避免每次改一条诗词都重下 100 MB；
- 差分包（可选）：服务端保留最近 3 个版本，生成 `bsdiff` 风格的二进制差分包，客户端校验「旧版本 → 新版本」；
  差分失败自动回退全量。第一版不做。

## 4. 下发与客户端流程

```text
启动 / 每 24h / 手动检查
        │
        ├── 离线？→ 跳过（不发请求）
        │
        ├── GET /v1/content/manifest?sn=…&version=…&channel=…
        │       （带 If-None-Match，304 直接结束）
        │
        ├── 云端版本 ≤ 本地？→ 结束
        │
        ├── 灰度命中？minAppVersion 满足？→ 否则结束
        │
        ├── 仅 Wi-Fi / 充电 / 剩余空间 ≥ 1 GB？→ 否则排队等下次
        │
        ├── 下载到 files/content/download/，支持断点续传（Range + ETag）
        │
        ├── 校验整包 SHA-256 + 清单签名 + 文件逐个哈希
        │
        ├── 解压到 files/content/staging/<version>/
        │
        ├── 原子切换：current → <version>（旧版本保留为 previous）
        │
        ├── 写 contentVersion、清理 staging、保留一个旧版本
        │
        └── 上报 content_update 事件（成功/失败原因/耗时/包大小）
```

关键决策：

- **不阻塞启动**：检查和下载都在后台线程，主页先用本地内容；
- **原子替换**：任何一步失败都不动 `current`，下次继续；
- **先空间后下载**：`minFreeBytes` 由服务端给，客户端再结合本地实际空间取最大值；
- **失败的退避**：1 次失败 1 小时后重试，连续失败 24 小时后再试，最多 3 次自动重试；
- **不重复下载**：ETag/版本号一致直接 304；
- **可关闭**：设置里提供「内容自动更新」开关，关闭后只检查不下载。

## 5. 磁盘与流量预算

| 项 | 上限 | 说明 |
| --- | --- | --- |
| 内容包 | 200 MB | 超过直接拒绝，后台也不允许上传 |
| 临时目录 | 1 个包 | 下载失败/中断时下次覆盖 |
| 当前版本 | 1 份 | `current` |
| 旧版本 | 1 份 | `previous`，仅用于回滚，7 天后清理 |
| 最小剩余空间 | 500 MB–1 GB | 服务端 `minFreeBytes` 与设备实际空间取大 |
| 检查频率 | 24 小时 | 或手动检查，不随启动反复请求 |
| 下载并发 | 1 | 不与遥测/反馈抢带宽 |
| 失败重试 | 3 次 | 指数退避，之后等下次启动 |

词库单独一套预算：英汉词库 86 MB、汉语 15 MB，两者更新时只下载变化的那一份，且默认只在 Wi-Fi + 充电时进行。

## 6. 灰度与回滚

- 服务端按 `SHA-1(sn) % 100 < rollout` 命中；同一 SN 结果稳定；
- 后台提供「设备白名单/黑名单」覆盖灰度结果，用于教研组试点或问题设备排查；
- 内容版本可以独立回滚：把 `contentVersion` 指回上一版，客户端发现云端版本低于本地时**不自动降级**，而是等下一次「强制回滚」标记；
- 强制回滚通过 `/v1/config` 的 `content.rollbackTo` 下发，客户端确认后切回 `previous`；
- 每次发布/回滚都写审计日志，并记录下载成功率与失败原因。

## 7. 后台需要新增的页面与接口

### 后台页面

- 内容版本列表：版本号、包大小、文件数、发布时间、灰度、状态（草稿/生效/回滚）；
- 上传与校验：上传 ZIP，服务端计算哈希、列文件、检查路径与大小、预览差异；
- 灰度控制：比例、白名单、黑名单、最低客户端版本；
- 设备覆盖：按 SN 看当前内容版本、上次检查、下载失败原因、磁盘余量；
- 回滚与删除：保留最近 N 个版本。

### 服务端接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/v1/content/manifest?sn=&version=&channel=` | 返回清单或 304；按 SN 灰度 |
| GET | `/v1/content/download/:version` | 支持 Range、ETag、Content-Length；只读对象存储/本地文件 |
| POST | `/v1/telemetry/events` | 复用现有事件，新增 `content_update` 事件 |
| 管理端 | `/api/content/*` | 上传、发布、灰度、回滚、设备覆盖、审计 |

### 存储

- 内容包放对象存储（校内 MinIO / OSS）或本机 `data/content/`，**不要放 SQLite**；
- 清单可以放 DB，方便灰度和审计；包文件按 `version/sha256` 命名，不可变；
- 旧包保留最近 3 个版本，超出清理。

## 8. 安全

1. 全链路 HTTPS；下载地址带短期签名或 CDN 防盗链；
2. 清单与包使用 Ed25519 签名，客户端内置公钥；签名失败直接拒绝；
3. ZIP 解压防路径穿越（拒绝 `..`、绝对路径、符号链接）；
4. 只允许清单里出现的文件，解压后逐个校验 SHA-256；
5. 内容只包含数据与静态 HTML，不执行下载的代码；
6. 服务端限制上传类型、大小、文件数，并做一次语法/结构校验（JSON 可解析、HTML 无脚本注入风险）。

## 9. 与现有系统的衔接

- `CloudControl` 增加 `content` 状态与 `checkContent()`，与配置同步共用「在线判断 + 退避 + 日志」；
- `FileContentRepository` 从「读 assets」改成「优先读 `files/content/current`，没有就回落到 assets」；
- 首启仍复制 APK 内词库；内容更新只改 `files/content`，不碰 APK；
- 版本提示继续只提示 APK 版本，内容更新不弹窗，只在设置里显示「内容版本/检查更新」；
- 遥测新增 `content_check`、`content_download`、`content_apply` 事件，后台可看成功率；
- 所有下载都遵守「无网络不请求、Wi-Fi 优先、磁盘上限」三条约束。

## 10. 分阶段落地建议

| 阶段 | 范围 | 预估 |
| --- | --- | --- |
| P1 | JSON 内容（诗词/语法/方程式/公式）全量包 + 清单 + 灰度 + 回滚 | 3–5 人日 |
| P2 | 断点续传、签名、失败退避、后台内容页 | 3–4 人日 |
| P3 | 词库分包、差分包、下载统计与告警 | 5–8 人日 |
| P4 | CDN/对象存储、灰度自动化、回滚演练 | 视部署环境 |

先做 P1 即可覆盖绝大多数「改一条诗词、补一条公式」的需求；词库更新频率低，值得单独排期。

## 11. 不做的部分

- 不做 APK 自更新（学校市场统一安装）；
- 不做任意代码/插件下发；
- 不做后台远程删除用户本地内容（只能切版本，旧版本保留可回滚）；
- 不做 P2P/CDN 之外的复杂分发。
